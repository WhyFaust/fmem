# Проверки памяти

## Автоматические хуки

Прогон через настоящий Codex 0.172.0-alpha.2 использует отдельные профиль,
проект и vault. Локальная заглушка Responses управляет ходами; платная модель
и внешние сервисы в проверке не участвуют. Для семантики используется настоящая
локальная ONNX-модель. Ни один сценарий не обращается к рабочему vault.

```bash
python scripts/check_codex_hooks.py --fmem target/release/fmem --codex /path/to/codex
python scripts/check_codex_agents.py --fmem target/release/fmem --codex /path/to/codex
python scripts/check_semantic_hooks.py --fmem target/release/fmem --codex /path/to/codex \
  --model-source /path/to/model-files --runtime /path/to/libonnxruntime.so \
  --output /path/to/semantic-hooks.json
```

Первые две команды входят в Linux CI. Они проверяют установку, доверие,
Plan, одну попытку восстановления пропущенного staging, настоящий
PostToolUse, Interrupt и вложенность агентов второго уровня. Принятая операция
проверяется до Stop и после него. Заглушка задаёт кандидат записи заранее:
эти тесты проверяют протокол, а не качество отбора знаний языковой моделью.

Семантический сценарий отдельно устанавливает модель из локальных файлов,
проверяет отрицательный лексический контроль и запускает обычные задачи Codex.
В нём нет ручной команды индексации. Асинхронный хук сам строит векторы четырёх
записей, после чего RU/EN перефразировки приходят в контекст агента. Внешняя
правка подхватывается автоматически, забытая запись исчезает, повторные запросы
используют один фоновый процесс. Plan этот процесс не запускает.

В наблюдаемой серии из 11 прогретых запросов синхронный хук занял **68 мс по
медиане и 102 мс по p95**. Время включает оболочку, старт CLI, обмен с worker
и retrieval; генерация ответа не входит. Первый семантический контекст появился
через 7,204 с после начала холодного сценария. Это время готовности фоновой
модели; первые запросы продолжали работать лексически. Внешняя правка попала
в контекст через 2,683 с в этом прогоне. Корпус мал, файловый кеш ОС не сбрасывался,
и результаты не задают гарантию задержки на другом vault или компьютере.

На Windows 11 x64, AMD Ryzen 7 5800X и установленном Codex 0.157.1 этот сценарий
прошёл в отдельном профиле с read-only sandbox и отключённой сетью. Настоящая
локальная модель использовала четыре заметки; лексический контроль обеих
перефразировок был пуст. Из 11 прогретых полных sync-хуков медиана составила
**576 мс**, p95 — **692 мс**. Время включает PowerShell, процесс, IPC и поиск.
Лимит 150 мс относится только к запросу через IPC. Первый семантический контекст
появился через 4,579 с, внешняя правка — через 3,649 с. Процесс остался тем же,
Plan его не запускал, забытая запись отсутствовала, незапрошенных записей не было.

Один предыдущий Windows-прогон завершился несовпадением числа запросов к
заглушке при восстановлении Stop: получен один запрос вместо двух. Состояния
хуков в том прогоне не сохранились; причина не установлена. Повтор с тем же
бинарником и прежними условиями проверки прошёл. При таком несовпадении
скрипт теперь выводит тип, статус и длительность хуков для диагностики.

Для измерения нативного цикла без клиента и embedding-модели:

```bash
python scripts/benchmark_hooks.py --binary target/release/fmem \
  --records 1000 --samples 11 --output /path/to/hooks.json
```

## Качество retrieval

[Корпус и наблюдаемые результаты](verification/retrieval-corpus.json) содержат
два вымышленных проекта, одно общее предпочтение, заменённое правило и семь
RU/EN вопросов с заранее выбранной целевой записью. Дополнительный вопрос
о выпечке проверяет поведение на посторонней теме. Для повторения создай записи
по `key`, связывая `supersedes` с выданным ID, выполни `index --semantic` и
передай вопросы в `memory_context` с `limit=3`, `max_bytes=4000`.

| Режим | Целевая запись в top-3 | Целевая запись в top-1 |
| --- | ---: | ---: |
| Лексический | 2 из 7 | 2 из 7 |
| Семантический | 6 из 7 | 4 из 7 |
| Гибридный | 6 из 7 | 4 из 7 |

Английская перефразировка об откате релиза не вывела нужное русское правило
в первую тройку. Вопрос о выпечке получил три близких вектора, хотя подходящей
записи в корпусе нет. Косинусное сходство и RRF не выражают уверенность в
применимости. Выдача остаётся набором кандидатов: агент проверяет содержание,
читает полную запись и отбрасывает несвязанные результаты. Эти семь вопросов
дают контрольный пример, а не универсальную оценку точности.

Области проектов, общие предпочтения, замена и забывание прошли отдельные
контроли. Внешняя правка немедленно исключает прежний вектор; новый появляется
после фонового прохода. Тест с бюджетом 2000 байт сохранил две короткие записи
предпочтений и один результат, установив признак усечения.

## Нативный цикл на 1000 заметках

Linux 6.18.57 x86_64, Intel Xeon Platinum 8573C, 9 доступных логических CPU,
Rust 1.90.0, release-сборка. Корпус содержит 1000 синтетических решений.
Скрипт делает один прогрев и 11 измерений полного цикла prompt → stage skip → Stop.
В него входят процесс, JSON, актуализация FTS, recall и состояние хода.
Оболочка Codex, модель и создание корпуса в измерение не входят.

Для формата с читаемыми именами `Records/ID/Заголовок.md` измерены:

| Шаг | Медиана, мс | p95, мс |
| --- | ---: | ---: |
| UserPromptSubmit | 35,409 | 38,959 |
| Stage skip | 3,466 | 5,043 |
| Stop | 4,284 | 7,209 |

На том же корпусе плоское расположение файлов дало 17,993 мс по медиане
и 20,847 мс по p95 для prompt. Читаемые имена добавили около 17 мс:
обход проверяет отдельные каталоги ID. Поиск файла по ID проверяет только его каталог; актуальность записи с учётом
замен и удаления определяется по статусам области. Идентификаторы, контрольный recall и отсутствие
новых записей после skip проверяются в обоих сценариях.

p95 вычислен ближайшим рангом и при 11 образцах равен максимуму. Файловый
кеш ОС между запросами не сбрасывался. Эти измерения описывают конкретный
корпус и компьютер; они не задают гарантию для другого vault.

## Представления Obsidian

В Obsidian 1.15.1 на Windows проверен отдельный демонстрационный vault:
главная показывает два проекта, два кандидата Inbox и четыре сохранённые
версии; страница проекта — свой Inbox, две версии и действующую ссылку
на предшественника. В графе девять узлов с читаемыми именами, без Home,
списка проектов и файлов Bases. Скриншоты README сняты в настоящем приложении.

Rust-регрессии проверяют одинаковые заголовки, Unicode, имена Windows,
переименование внутри каталога ID, повреждённые и неоднозначные каталоги,
ссылки исправлений, историю, индекс и повторную доставку операций.
Инициализация сохраняет существующие закладки и настройки обычного графа;
пользовательский CSS с совпадающим именем не включается автоматически.

## Семантический и гибридный поиск

Выполнен тест на CPU с `intfloat/multilingual-e5-small` FP32 ревизии
`614241f622f53c4eeff9890bdc4f31cfecc418b3` и ONNX Runtime 1.22.0.
ONNX-файл весит 470 268 510 байт. Тест запускает локальную модель после
проверки SHA-256 пяти файлов и установки во временный каталог.

```bash
FMEM_TEST_MODEL_SOURCE=/path/to/model-files \
ORT_DYLIB_PATH=/path/to/libonnxruntime.so \
cargo +1.90.0 test --locked --lib multilingual_model_recovers -- --ignored --nocapture
```

`FMEM_TEST_MODEL_SOURCE` указывает на локальную копию файлов из ревизии
модели. Если уже выполнен `fmem model install`, можно вместо исходной папки
задать `FMEM_TEST_MODEL_STATE` с путём к локальному состоянию fmem. Если
ONNX Runtime установлен там же, `ORT_DYLIB_PATH` можно опустить.

| Запрос | Результат top‑1 в semantic и hybrid | Косинусное сходство semantic |
| --- | --- | ---: |
| Как переслать заказ клиенту? | Порядок доставки | 0,838 |
| Where do I book time off work? | Vacation request | 0,846 |

Лексический поиск не вернул совпадений для этих двух запросов на наборе из
четырёх записей. Повторная индексация сохранила готовые векторы. При добавлении
новой записи гибридный режим возвращает лексическое совпадение и сообщает,
что часть записей ждёт семантической индексации. Инкрементальный проход
вычисляет один недостающий вектор.
